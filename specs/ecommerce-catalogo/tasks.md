# Tareas — Catálogo de obras y ediciones

> Tareas atómicas ordenadas **de adentro hacia afuera**: Dominio → Aplicación → Infraestructura → Api → Web → pruebas de integración y E2E. Cada tarea cabe en un commit, empieza con una prueba que falla y deja el proyecto compilando. Cada criterio de aceptación de la spec aparece en al menos una tarea. Todo vive en el módulo `Catalogo` del E-commerce y en la interfaz web.
>
> **Nivel de rigor** (`docs/07-proceso-de-desarrollo/05-desarrollo-por-bloques.md` §2) tras la capa: `C` crítico (archivos digitales, autorización, auditoría, stock y su integración, roles de base de datos, secretos), `E` estándar, `B` bajo; el nivel lo manda la parte más riesgosa de la tarea. **Bloques propuestos** (4 a 10 tareas): `ECO-2a` = T01 a T06 (C, dominio y puertos); `ECO-2b` = T07 a T13 (C, casos de uso; se cierra con dobles de auditoría); `ECO-2c` = T14 a T23 (C, infraestructura, Api y pruebas de integración; se cierra con la persistencia real de la auditoría); `ECO-2d` = T24 a T28 (B, C y E: las pantallas de subida y de ingreso son C, el resto E; pantallas y E2E, después de `WEB-1`). **Dependencias:** AUD-2 (contratos y catálogo de acciones de `IAuditoria`) y AUD-4 (su persistencia real, que cierra T22), la ampliación de `IClienteDelInventario` en `Plataforma` (registrar edición, disponibilidad por lotes y los dos ingresos; carril A), el contenedor, la credencial y la regla de ciclo de vida del almacén del catálogo (`infra/almacen/`, carril A), IDE-2 (contrato de Identidad para el nombre del usuario del historial), `ITokenDelUsuarioDeLaSesion` y `WEB-1` para las pantallas e INV-1 e INV-3 para la prueba de contrato; hasta entonces las pruebas usan dobles de esos puertos. Cierres diferidos a otras features: AC-CAT-05 (accesos, `ecommerce-biblioteca-digital`, ECO-8), AC-CAT-10 (pedidos históricos, `ecommerce-pedidos`, ECO-6) y AC-CAT-15 (carritos y aviso visible, `ecommerce-carrito-checkout`, ECO-4); aquí se prueba lo que el Catálogo controla.
