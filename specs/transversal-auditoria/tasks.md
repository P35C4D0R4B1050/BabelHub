# Tareas — Auditoría y eventos de seguridad

> Tareas atómicas ordenadas **de adentro hacia afuera**: Dominio → Aplicación → Shared → Infraestructura → Api → Web → pruebas de integración y E2E. Cada tarea cabe en un commit, empieza con una prueba que falla y deja el proyecto compilando. Cada criterio de aceptación de la spec debe aparecer en al menos una tarea. Lo difícil (inmutabilidad, ventanas y paginación estable) va antes. Todo vive en el módulo `Auditoria` de cada servicio; las piezas de `Plataforma` (`IReloj`, `IActorActual`, `IUnidadDeTrabajo`, `IEnviadorDeCorreo`) se consumen por su contrato y se construyen antes (`transversal-seguridad` T04 y `identidad-seguridad` T30). **Orden entre planes:** T07 de este plan, luego `identidad-seguridad` T11 (contrato de correo) y T34 (adaptador), luego T18 y T27 de este plan. Esta feature entrega el catálogo de acciones y su contrato; la llamada a `IAuditoria` de cada operación sensible la agrega el plan de su feature.

Formato de cada línea: `- [ ] T01 [Capa] Descripción (cubre: AC-XXX-01, XXX-01)`.

- [x] T01 [Dominio] `DetalleSeguro`: lista blanca de claves por acción, redacción (no rechazo) de valores con forma de tarjeta, token, enlace o dirección, marca de personales por clave y truncado a 1000 caracteres con marca sin dejar un valor personal sin marcar (cubre: AC-AUD-05, AC-AUD-20, AUD-06, AUD-24)
- [x] T02 [Dominio] Catálogo de acciones con su clase (concede o cambia / no concede), claves permitidas del detalle, si su objeto, su rol y cada clave son personales (obligatorio) y motivos de catálogo cerrado; `PlantillaDeRuta` (plantilla sin parámetros, `;` ni fragmento, con tope y `sin-coincidencia`) (cubre: AC-AUD-01, AUD-01, AUD-02)
