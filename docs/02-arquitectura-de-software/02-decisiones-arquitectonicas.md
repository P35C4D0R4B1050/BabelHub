Cada decisión indica el driver que la motiva ([drivers arquitectónicos](01-drivers-arquitectonicos.md)), por qué se eligió y qué alternativa se descartó. Las decisiones de despliegue (AD10 a AD14, AD16 y AD31) se desarrollan con más detalle en [despliegue](05-despliegue.md).

## 2. Decisiones de software en detalle

**Sobre AD01 y AD02.** Dos servicios no significan pocas capacidades: cada uno agrupa muchas. El E-commerce reúne catálogo, carrito, checkout, pagos, pedidos, envíos, devoluciones, biblioteca digital, reclamaciones, identidad y asistente porque comparten ciclo de vida, usuarios y despliegue, y no necesitan escalar de forma independiente. Solo el inventario justifica un servicio aparte. La separación se pensó con ojos de arquitectura, no de organigrama: lo que se separa es lo que debe poder fallar, desplegarse y probarse por separado.

**Sobre AD03 y AD18.** El estilo basado en servicios suele compartir una base entre servicios; la base por servicio es la regla de los microservicios. Se eligió el punto intermedio: una base por servicio en una sola instancia. Dentro del E-commerce, un esquema por módulo con un rol por esquema da el aislamiento necesario entre módulos y deja las transacciones entre ellos en una sola base. Identidad es un esquema aislado por rol y no una tercera base (ver la comparación en [despliegue](05-despliegue.md) §5).

**Sobre AD11.** El estilo no exige una VM por servicio; exige que cada servicio se pueda desplegar por separado, y lo es. El reparto responde a capacidad y riesgo: el Inventario no compite por CPU con la venta, la entrada pública cabe en una AMD micro y la réplica de gestión mantiene operativo al personal si cae la VM de ventas. **Riesgo aceptado:** la base comparte VM con el Inventario; si cae esa VM, cae todo el sistema. Se mitiga con respaldo y WAL en el almacén de objetos y con defensa en profundidad (AD31). Una tercera VM ARM de pago para PostgreSQL es un cambio de Compose, no de código.

**Sobre AD08.** Si el stock se validara y se reservara solo después de pagar, dos clientes podrían pagar la misma última unidad. Reservar antes con un tiempo límite elimina ese caso, a cambio de un proceso que libera reservas vencidas. Es una mejora a la propuesta original, ya validada con el docente.

**Sobre AD15.** La interfaz es una sola aplicación con tres áreas (Tienda para el cliente, Sucursal para encargados y logística, Admin para la administración central), servida en dos hosts: la tienda y la gestión del personal. Vive dentro del E-commerce porque comparte diseño, sesión y despliegue. Los navegadores nunca llaman a los servicios: lo hace el servidor. La sesión vive en la base para que una réplica de gestión la comparta. La API del Inventario no tiene entrada pública: solo la llama el E-commerce.

**Sobre AD16.** El flujo es: servicio → webhook de n8n → Evolution API → WhatsApp. El adaptador del servicio no espera al envío: si n8n no responde, registra el aviso como pendiente y se reintenta, de modo que la compra nunca se bloquea. Evolution API usa la Redis existente y la base `evolution` de la instancia PostgreSQL. n8n guarda sus datos en un volumen (SQLite), y sus flujos se exportan a `infra/n8n/` para versionarlos. Sus paneles se alcanzan solo por túnel SSH.

**Plan de salida de WhatsApp (AD16).** Evolution API no es un canal oficial: el número puede bloquearse o el protocolo cambiar sin aviso. Señal de alerta: avisos que fallan tras todos los reintentos (NOT-04) de forma sostenida. Salida: cambiar solo el adaptador del puerto `Notificador` hacia la API oficial de WhatsApp Cloud (requiere cuenta de negocio y plantillas aprobadas, con costo por conversación) o hacia correo transaccional (ampliando RC18 y NOT). No cambian las specs de negocio ni los servicios. No se implementa ahora (decisión 2026-10-16); entretanto, los pedidos y traslados se consultan siempre en la tienda y el aviso no es la única vía de información.

**Sobre AD17.** Culqi también permite reembolsos, que usa `ecommerce-devoluciones`. Los detalles de idempotencia, Yape y modo de pruebas (llaves de sandbox) se confirman con la documentación de Culqi al escribir la spec de pagos.

**Sobre AD19 y AD20.** Un libro digital es una **edición** del mismo título, con su propio ISBN, y vive solo en el E-commerce: no tiene stock, ni reserva, ni fuente, ni traslado, por lo que su compra no depende del Inventario. Un pedido agrupa **líneas**: las impresas siguen el ciclo de reserva, preparación y entrega; las digitales pasan a *acceso concedido* en cuanto se aprueba el pago. Un pedido mixto cobra una sola vez. La descarga sigue este camino: el cliente pide el archivo, el E-commerce comprueba que es el titular y que no superó el límite, genera una URL firmada de pocos minutos y el navegador descarga directamente del almacén. La Web nunca recibe el archivo. El catálogo digital guarda titular de derechos, territorios y vigencia de la licencia (RF24). El marco legal está en [marco legal](../01-analisis-de-sistema/03-marco-legal.md). **Alcance académico:** la administración sube directamente los EPUB y PDF al almacén de objetos (CAT-16); no se integran enlaces ni catálogos externos de editoriales, y la licencia de cada título (titular, territorio y vigencia) se registra con datos de ejemplo. Los archivos nunca se guardan en las VMs ni en la base de datos: la base solo guarda su clave en el almacén y su huella SHA-256.
